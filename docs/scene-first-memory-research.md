# Scene-first memory: research note

**Checked:** 2026-08-14
**Question:** Is Titan’s model—an addressable extracted Memory linked to a durable Scene containing the evidence and context—established practice or distinctive?

## Short answer

The ingredients are established separately. Research systems store episodic experience streams and derive semantic memories; event-sourced systems retain ordered events; provenance standards model derivation; RAG systems retrieve indexed passages; and agent-memory products combine some of these ideas.

Titan’s potentially distinctive contribution is the **explicit invariant and API shape**: a semantic Memory is a compact, addressable projection, while its Scene is a first-class durable record of the interaction that produced it. The Scene survives even when extraction produces no Memory, preserves ordered messages/tool calls and source-event lineage, and is the normal expansion path for checking the Memory. The closest public analogue found is **Zep/Graphiti**, whose episodic subgraph stores raw input and links derived semantic entities/relations back to episodes. I did not find another compared system that states Titan’s full contract as clearly. This is a claim about the combination and explicit contract, not proof that no unpublished or inaccessible system does it.

## Established patterns

### Episodic/experience memory and semantic abstraction

- **Generative Agents (Park et al., 2023)** stores a comprehensive natural-language memory stream of experiences. Each memory object has a description, creation timestamp, and most-recent-access timestamp; retrieval combines relevance, recency, and importance, while reflection synthesizes higher-level inferences. This establishes “retain experiences, derive abstractions, retrieve a compact subset,” but the paper does not define a separately addressable evidence container behind each abstraction. ([paper](https://arxiv.org/abs/2304.03442), especially §§2–3.)
- **MemGPT (Packer et al., 2023)** separates main context from external context. Its external context has **recall storage** for the entire event history and **archival storage** for facts, experiences, and preferences; retrieval moves selected external data back into context. This is a strong precedent for tiering and full-history retention, but recall and archival storage are separate memory tiers rather than a documented per-fact `memory -> source scene` contract. ([paper](https://arxiv.org/abs/2310.08560), §§2.1–2.3.)
- The general cognitive distinction—episodic records versus semanticized concepts—is therefore well established. The newer systems operationalize it as raw events/messages plus extracted facts, summaries, reflections, or graph relations.

### Event sourcing and provenance

- **Event sourcing** stores the full ordered series of changes in an append-only event store and derives current state from those events. It supports replay, temporal queries, and audit history, but it is a state-management pattern, not a memory-extraction method. ([Microsoft Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing), checked 2026-08-14; see also Fowler’s original [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html), 2005.)
- **W3C PROV** standardizes provenance as entities, activities, and agents connected by relations such as `wasGeneratedBy`, `used`, `wasDerivedFrom`, `wasQuotedFrom`, and `hadPrimarySource`. This makes “an extracted record points to the material/process that produced it” a recognized provenance pattern, independent of agent memory. ([PROV-O Recommendation](https://www.w3.org/TR/prov-o/), 2013.)
- Titan is **event-sourcing-adjacent**, not automatically a full event-sourced system: it has append-only, idempotently ingested trace events and durable scenes with lineage, but the claim that every materialized state can be rebuilt solely by replaying the event log would need an explicit replay guarantee and tests.

### RAG, grounding, and citations

- The original **RAG** formulation combines parametric model memory with a non-parametric dense vector index of passages. The retriever returns passages; the generator conditions on them. The paper explicitly identifies provenance for model decisions and knowledge updates as open problems. ([Lewis et al., 2020](https://arxiv.org/abs/2005.11401).)
- RAG systems commonly attach source metadata to retrieved chunks. For example, LangChain’s `Document` abstraction stores text plus metadata such as source, page, and offsets. That supports citation/grounding, but a chunk’s metadata is not necessarily a durable, reconstructible interaction scene. ([LangChain knowledge-base docs](https://docs.langchain.com/oss/python/langchain/knowledge-base).)
- The distinction matters: **citation/grounding answers “which indexed passage was retrieved?”; scene-first memory answers “which durable interaction and source events produced this extracted memory, and can I inspect them?”** They overlap in provenance but solve different retrieval and audit problems.

### What the comparison supports

1. “Store an experience/history and derive a smaller semantic memory” is established practice.
2. “Keep raw source material and provenance behind derived facts” is established in provenance systems and is explicit in Graphiti/Zep.
3. “Retrieve a compact semantic item, then inspect its durable originating interaction as a standard second step” is less common as an explicit agent-memory API contract. In the public systems checked, it is usually implicit, split across tiers, represented as history/audit logs, or left to application code.

## What seems distinctive in Titan

Verified against Titan’s local [architecture vocabulary](../CONTEXT.md), [storage models](../app/storage/models.py), and [retrieval pipeline](../app/retrieval_pipeline/brief.py):

- **Scene is first-class at the trace boundary.** A Scene is the durable interaction boundary for a trace segment and remains durable even if extraction yields zero Memories. Current pipeline writes associate extracted Memories with the Scene; the schema keeps `scene_id` optional for compatibility with legacy/other sources. This is stronger than storing source context only as incidental metadata on a successful extracted fact.
- **Memory is explicitly a projection/pointer, not the final evidence.** A Memory has a stable ID, extracted text, optional embedding, provenance, source-event IDs, reliability/verification fields, and—when produced through the scene-aware path—a `scene_id`. Retrieval can expand selected memory IDs into scene notes or full scene context.
- **The Scene model is designed to retain reconstruction material.** It contains ordered messages, compact tool-call records, a raw-event field, the event IDs/sequence range, and the exact user/assistant text offered to extraction. This makes the extraction boundary inspectable, not merely the original conversation in an unrelated log. There is an important implementation caveat: the current `_scene_raw_events()` path returns an empty list, so the event ledger—not `Scene.raw_events`—is currently the stronger source for exact reconstruction.
- **The design connects three granularities:** append-only trace events → durable Scenes → extracted Memories. Graphiti/Zep has a similar raw-episode → semantic-graph relationship, but Titan’s unit is a conversation/trace scene and its public contract is centered on resolving a retrieved Memory back to that scene.
- **The claim should be phrased narrowly.** “Titan invented evidence-linked memory” is not supported. “Titan makes evidence-linked scene expansion a first-class, durable invariant in a coding-agent memory system” is supported by the current repository and appears distinctive among the public systems reviewed.

## Limitations of claiming memory is solved

- **Extraction is lossy and model-dependent.** A Memory may omit qualifications, disagreement, uncertainty, or the reason a decision changed. A Scene preserves input, but it cannot restore information never captured by the adapter or extractor.
- **Lineage is not truth.** A source-event or scene link proves origin, not correctness. User claims, assistant claims, tool output, and inferred summaries need different reliability and verification policies.
- **Retrieval can fail before scene expansion.** If the right Memory is not admitted, embedded, indexed, scoped, or ranked, the right Scene is never reached. Scene-first improves inspectability after selection; it does not solve admission or ranking.
- **Durability has operational costs.** Full scenes/tool traces increase storage, migration, privacy, deletion, redaction, and secret-handling obligations. “Preserved” must include retention and erasure semantics, not only a database row.
- **A scene is not automatically complete.** Titan’s tool-call model intentionally stores compact summaries/excerpts rather than every raw tool output in the Scene object. The event ledger may be the stronger source, and the contract should state when reconstruction is exact versus approximate.
- **The systems are not directly benchmark-equivalent.** Generative Agents, MemGPT, Zep, Mem0, LangGraph, and LlamaIndex optimize different tasks and expose different layers. Public documentation is not proof of absence of an internal feature, and moving repositories/docs can drift. This note therefore reports explicit documented behavior, not undocumented internals or marketing claims.
- **No comparative Titan evaluation was found in this repository.** The distinctiveness conclusion is architectural and documentary. It is not a measured claim that Titan has higher recall, faithfulness, latency, or user value than the compared systems.
- **The current reliability path is incomplete.** The save pipeline appends retry records when extraction fails, but the current `app/` code has no retry-queue consumer/replayer; it advances the session checkpoint after queuing the failure. That means the recovery contract is not yet as strong as the scene-first model suggests. Separately, the ODE reranker persists `tau` and learned weights but not the evolved `h` activation, so the long-term activation state is only partially durable.

## Open questions

- What is the formal Scene-boundary rule for long traces, nested tool calls, parallel branches, retries, and overlapping extraction windows?
- Which fields are lossless, which are summaries, and which source is authoritative when Scene content and the event ledger disagree?
- Should every Memory require exactly one Scene, allow multiple Scenes, or support a derivation graph for memories merged/deduplicated from several scenes?
- How are memory updates, contradictions, supersession, and deletion represented without breaking stable Memory IDs or provenance links?
- Can retrieval expose a compact citation bundle: Memory ID, Scene ID, source-event IDs, extraction text, verification status, and the exact evidence excerpt used by the answer?
- What benchmark should measure the actual promise: retrieve the right Memory, expand the right Scene, recover the relevant evidence, distinguish fact from inference, and abstain when the Scene is insufficient?
- What privacy model governs full-scene retention—secret redaction, user deletion, per-agent namespaces, encryption, and auditability—especially when traces contain tool output or repository data?

## Sources and scope note

Primary sources were preferred: papers, official standards, official product documentation, and first-party repositories. Source pages were checked on **2026-08-14**. The comparison is intentionally limited to what those sources explicitly say they store and retrieve. Where a system’s public materials do not state a Memory-to-scene reconstruction contract, this note says so rather than inferring that the feature does not exist internally.
