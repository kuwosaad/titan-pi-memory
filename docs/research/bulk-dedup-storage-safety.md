# Safe storage deduplication: scan, review, apply, rollback

## Finding

The repository already prevents new same-ID memory duplicates in SQLite (`id TEXT PRIMARY KEY`) and rejects a same-ID payload collision rather than overwriting it. Historical JSON may still contain duplicate IDs, and current JSON append deliberately preserves those rows. This makes a cleanup command a data migration, not routine compaction. There is no basis in this checkout to estimate actual user-store savings: this task did not inspect live memories or measure their files.

## Storage and identity invariants

- Runtime context resolves one agent's `base_dir` and `memory_db_path`; defaults place its database under `<base_dir>/out/memories/memory_store.db` (`app/runtime/context.py:158-190`). Agent identity comes from `TITAN_AGENT_NAME`, and agent dotenv is loaded from `<TITAN_HOME>/agents/<agent>/.env` (`app/runtime/context.py:140-156`). Repository guidance requires each agent's writes to stay in its own `~/.titan/agents/<agent>` namespace and cross-agent reads to retain source identity (`AGENTS.md`). A scan/apply plan therefore needs a canonical namespace path plus agent name, and must never merge equal IDs across namespaces.
- Memory immutable derivation identity currently comprises ID, text, type, stream, session/turn, scene, source type/reliability, verification/fallback, source event IDs, provenance, speaker focus, kind, and embedding (`app/storage/memories.py:159-206`). `source_agent` is normalized but notably is not in `_MEMORY_IDENTITY_FIELDS`; it must still be retained and reported as provenance during cleanup, especially for federated records. Do not treat equal text or embeddings as duplicate identity.
- SQLite memory rows have `id TEXT PRIMARY KEY`, scene/session metadata, event lineage JSON, and embedding blobs (`app/storage/memories.py:391-424`). Embeddings are packed float32 (`:71-88`); a vector with dimension `d` occupies `4*d` raw payload bytes, excluding record/page/index overhead. SQLite uniqueness means duplicate row IDs cannot exist inside one normally initialized `memories` table; identical derivations with different IDs are separate memories and cannot be safely collapsed by current identity rules.
- JSON has a different legacy shape: append builds a list of all rows by ID, leaves historical duplicates untouched, accepts a matching existing derivation, and rejects collisions (`app/storage/memories.py:261-296`). Its read/count paths count every row (`:298-311`). A JSON cleanup must preserve ordering and all unselected rows byte-for-byte where possible; parse-and-reserialize may change formatting and destroy forensic evidence even if semantic content is unchanged.
- Scenes are separately stored as JSON or SQLite. SQLite uses `scene_id` primary key and serializes raw events, event IDs, missing IDs, messages, and tool calls (`app/storage/scenes.py:544-560`, `:595-610`). Complete scene validation binds ordered `source_event_ids` to raw-event IDs and requires an anchor (`app/storage/models.py:118-175`). Scene migration explicitly never promotes legacy evidence to complete (`app/storage/scene_migration.py:1-11`). Memory duplicate deletion must not delete, rewrite, or merge scenes, trace events, event indexes, or dedupe keys.
- The memory SQLite schema includes FTS5 external-content indexing and insert/delete/update triggers (`app/storage/memories.py:426-445`). Any row deletion through SQL must run with these triggers installed; bypassing them risks stale FTS results. Existing SQLite initialization can create/migrate schema (`:373-385`, `:447-464`), so an inspection path must not instantiate it with `initialize=True`.

## Proposed workflow

1. **Scan (read-only).** Resolve exactly one configured namespace; open SQLite with URI `mode=ro` (`app/storage/sqlite.py:37-53`) and never initialize absent stores (`app/storage/memories.py:373-388`). For JSON, open without calling `write_json`. Emit a deterministic report with store path, agent, backend, file hashes/size, duplicate groups, row offsets or stable IDs, complete canonical payload hashes, and references to scene IDs/source-event IDs. Separate exact same-ID/same-payload JSON duplicates from same-ID/different-payload conflicts. Do not group on text similarity. Include SQLite `page_size`, `page_count`, `freelist_count`, and WAL sidecar size as estimates, not a promise of savings.
2. **Review.** Write a plan artifact containing the scan fingerprint, namespace identity, keeper row, exact rows selected for removal, reason, and byte estimate. Require an explicit apply invocation to name that immutable plan. Refuse if source file hash/schema/row fingerprint changes since scan; re-scan and review instead. Ambiguous conflicts, incomplete scene evidence, absent provenance, and any cross-agent grouping are ineligible by default.
3. **Apply.** First create and verify a consistent backup/snapshot in the same namespace, including SQLite WAL-aware backup through SQLite's backup API (do not copy just the main file while active writers may exist). Store a manifest and exact removed row payloads in a separate receipt. Recheck plan fingerprint under a write lock/transaction, then perform one transaction per database. For JSON, write a sibling temp file, fsync, atomically replace, and retain original snapshot and full removed records. For SQLite, only delete reviewed duplicate IDs/rows whose payload hashes revalidate; triggers keep FTS synchronized. Never touch scene/event stores. Report logical rows/bytes removed separately from file bytes reclaimed.
4. **Verify and rollback.** Reopen read-only and verify surviving canonical payloads, all unaffected row hashes, FTS integrity/search behavior, SQLite integrity check, and lineage references. Rollback must be a separate explicit command that restores the snapshot or inserts exact removed records only if current store fingerprint permits it; do not silently overwrite post-apply writes. Keep the receipt until the user explicitly removes it.

## Cross-ID semantic consolidation (different memory IDs)

This is the likely space-saving case, but the current contract does not support it. `MemoryStore` exposes append and reads, with no update/delete/alias operation (`app/storage/repository.py:19-43`). Memory IDs are unique primary keys (`app/storage/memories.py:391-394`), and retrieval, graph weights, and external consumers may refer to those IDs. No in-repository foreign-key or redirect contract was found. Therefore the protocol below is a design requirement, not something that can safely be applied through current repository APIs.

1. **Propose, don't auto-merge.** Candidate grouping can use semantic similarity for review only. A reviewer must compare the complete text and evidence and list atomic claims from each memory. Merge only if every claim is preserved by a chosen canonical text or explicitly represented in an approved replacement. Similar wording, same embedding neighborhood, or overlapping source events alone is insufficient.
2. **Keep an existing canonical ID.** Retain one reviewed existing ID (prefer the oldest stable ID only as a deterministic default, never as proof of authority). Do not mint a new ID: that would invalidate every existing reference without providing a benefit. Preserve the canonical row's identity fields unless the reviewed replacement text genuinely needs an update; current storage has no update API and the canonical derivation function treats text, lineage, and embedding as immutable (`app/storage/memories.py:159-206`). Any actual text change therefore needs a separately designed migration contract.
3. **Preserve every source and provenance.** Receipt the exact full records for every member. Build a source-event union in stable order, but do not overwrite the canonical `source_event_ids` with this union: those IDs describe that memory's derivation and may point to different scenes/sessions. Preserve per-member `scene_id`, `session_id`, turn, provenance, source agent, reliability, verification, and timestamp in the receipt. `provenance` only has `user`/`assistant` strings and cannot safely encode a multi-scene evidence bundle (`app/storage/models.py:14-20`); a durable many-to-one evidence model or sidecar is needed before destructive consolidation. Do not alter scene records or claim the canonical memory is sourced by every event unless the storage model is extended to express that relationship.
4. **Keep aliases for removed IDs.** Before removing a noncanonical ID, require an alias/redirect lookup that maps every retired ID to the canonical ID, and update/verify all internal references (including graph `incoming_weights`/`outgoing_weights`, retrieval state, and any consumers outside this repo). The current schema stores weights as blobs and has no alias table or general reference-rewrite API (`app/storage/memories.py:414-417`; read/write protocol above). Until that seam exists and external references are accounted for, cross-ID groups are report-only. Never silently discard retired IDs.
5. **Compare byte savings in scratch copies.** For SQLite, first take a consistent SQLite backup to a scratch DB, apply the exact proposed deletes only to that copy (with schema/triggers intact), and run `VACUUM INTO` to a second scratch path. Compare original consistent snapshot size with compacted output size; include associated WAL/journal files separately and record scratch free-space needs. This measures the proposed resulting DB, including retained indexes/FTS, much better than multiplying row count by payload size. Do not `VACUUM INTO` the live DB or count its output as a guarantee for a later apply: writes, page layout, SQLite version, or concurrent activity can change the result. For JSON, perform the equivalent exact reviewed rewrite only in a scratch copy and compare bytes.
6. **Receipt enough for exact recovery.** The reviewed/apply receipt must store namespace/path, database schema/version and source fingerprint, candidate member records byte-for-byte or losslessly, canonical ID, retired-ID alias mapping, removed row IDs, source-event/provenance/scene manifest, edge/weight changes, before/after hashes and sizes, SQLite runtime version, scratch estimate, and verification results. Rollback restores the pre-apply snapshot only if the current fingerprint still matches the post-apply state; otherwise stop and require a fresh reconciliation. Keep retired-ID aliases and receipt for as long as references may exist.

**Fact-loss check:** before approval, render a claim-by-claim checklist with the source memory ID and exact source evidence for each claim, mark where each claim appears in the retained representation, and reject a group with any uncovered claim or disputed attribution. Then verify after apply that each source-event ID still resolves to its original scene/trace evidence and each retired ID resolves to the canonical memory through the alias layer. This can demonstrate representation and lineage preservation; it cannot prove semantic equivalence automatically. The repository has no existing many-to-one evidence/alias contract, so that uncertainty must remain explicit.

## Realistic space accounting

- **JSON logical deletion:** expected file-size reduction is approximately the serialized size of removed records plus separators/whitespace. If a compact rewrite is used, formatting changes can make the measured delta differ; report actual before/after bytes. No compaction distinction exists for JSON.
- **SQLite logical deletion:** a deleted record makes pages reusable but usually does not shrink the database file. A rough upper bound for pages already on the freelist is `PRAGMA freelist_count * PRAGMA page_size`; actual file shrink after rebuild is not known from row count, since retained rows, indexes, FTS data, free-page placement, and partial-page packing matter. Deleted embeddings contribute at most `4*d` payload bytes each before overhead, but do not imply equivalent file-size reduction.
- **SQLite `VACUUM`:** can compact remaining live content and remove freelist pages; estimate savings only after measuring a consistent copy with `VACUUM INTO` (or an isolated backup), comparing main DB and WAL state. Official SQLite docs say ordinary deletes leave free pages unless auto-vacuum FULL is enabled and `VACUUM` rebuilds the file; it may need up to twice the original DB size as temporary free space and can fail under locks/open transactions. See [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html) and [PRAGMA freelist_count](https://www.sqlite.org/pragma.html#pragma_freelist_count).
- Current Titan schema does not set `auto_vacuum` in its initialization path (`app/storage/memories.py:390-448`), so do not promise immediate shrink after `DELETE`. The SQLite API's ability to query page counts is a useful planning signal, not a precise reclaim estimate. WAL checkpoint/truncation is a separate operation with concurrency implications and should not be bundled into dedup apply.

### Synthetic scratch experiment

`tools/benchmarks/bulk_dedup_space_probe.py` creates two isolated temporary SQLite databases with synthetic memory-like rows (512-byte text, 768-dimension float32 vector, and 64 KiB each for both legacy LNN weight blobs). It compares 100/200 exact cross-ID duplicate row deletions with nulling both weight blobs on all 200 rows. On the current local SQLite build:

| Synthetic operation | Before | After SQL change | After `VACUUM` | SQL change reclaimed | `VACUUM` additionally reclaimed |
| --- | ---: | ---: | ---: | ---: | ---: |
| Delete 100 of 200 duplicate rows | 27,086,848 B | 27,086,848 B | 13,561,856 B | 0 B | 13,524,992 B |
| Null two 64 KiB weight blobs on 200 rows | 27,086,848 B | 27,086,848 B | 872,448 B | 0 B | 26,214,400 B |

Both scratch DBs passed `PRAGMA integrity_check`; FTS row count matched the remaining base rows after the duplicate delete. This confirms the mechanism, not Titan-user savings: ordinary delete/update left the main DB file the same size, while `VACUUM` reclaimed the freed pages. The weight case suggests legacy graph blobs could dominate byte recovery if real stores contain similarly large weights, but actual weight distributions and duplicate prevalence are unmeasured. The command accepts only numeric sizing parameters and uses `TemporaryDirectory`; it has no live-store path input. Reproduce with `python3 tools/benchmarks/bulk_dedup_space_probe.py`.

## Existing seams and minimal implementation

Useful existing seams: `SqliteMemoryRepository(..., initialize=False)` already supports non-materializing read-only inspection (`app/storage/memories.py:373-388`); `sqlite_connection(..., read_only=True)` uses `mode=ro` (`app/storage/sqlite.py:37-53`); `backfill_scene_evidence(apply=False)` demonstrates dry-run/apply reporting (`app/storage/scene_migration.py:1-11`); tests exercise dry-run immutability and idempotent apply (`tests/test_scene_migration.py:51-77`, `:136-195`). JSON's `load_all_memories()` is read-only but loses original lexical representation; a byte-preserving scanner needs its own parser/offset strategy.

Minimal future seam: a standalone storage-maintenance module/CLI that accepts an explicit namespace path and a scan-plan path, uses repositories only for canonical payload semantics, and owns plan validation, snapshot receipt, alias resolution, and apply/rollback. Keep it out of ordinary retrieval and ingestion. Add no automatic fuzzy dedup policy. Identical same-ID legacy JSON cleanup can be considered separately; semantically similar different-ID records must remain report-only until the durable evidence bundle, retired-ID aliasing, reference updates, and update/delete APIs exist.

## Risks to call out in implementation

- Shared/global configured DB paths can override the apparent agent-local default (`app/runtime/context.py:185-190`); identify actual resolved path and agent in every report and refuse a path shared by multiple identities unless explicitly supported.
- FTS trigger synchronization, concurrent writers, WAL files, and crash-safe backup/replace are correctness constraints, not optimizations.
- `source_agent` is not part of current canonical identity. A future cleaner must preserve it and avoid cross-agent equivalence assumptions.
- A duplicate memory may be referenced externally by ID even where this repository has no foreign key. The receipt and rollback must preserve original IDs/content; references must be audited before proposing row removal.
- Cross-ID consolidation can reduce persisted memory and embedding bytes, but the current storage model cannot represent multiple source scenes/provenance in one memory or preserve old IDs as aliases. The safe potential savings are therefore unknown until a concrete candidate set and migration model exist.
- JSON duplicate IDs can have different mutable LNN metadata even when derivation fields match; current append comment explicitly preserves such rows (`app/storage/memories.py:266-268`). Eligibility must inspect and preserve or explicitly account for mutable state (`h`, `tau`, outgoing/incoming weights), which are stored in SQLite columns (`:414-417`) but excluded from canonical derivation identity.
